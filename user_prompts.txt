## 5. Concurrency & atomic job claiming (the part evaluators care about most)

Each worker is a **separate OS process** (spawned via `child_process.fork`,
not just an async loop in one process — the assignment explicitly asks for
"worker processes"). All workers connect to the same SQLite file in WAL mode.

Claiming a job must happen as a single atomic UPDATE so two workers can never
grab the same row:

```sql
UPDATE jobs
SET state = 'processing', worker_id = @workerId, locked_at = @now, updated_at = @now
WHERE id = (
  SELECT id FROM jobs
  WHERE state IN ('pending', 'failed')
    AND (run_at IS NULL OR run_at <= @now)
    AND (next_attempt_at IS NULL OR next_attempt_at <= @now)
  ORDER BY priority DESC, created_at ASC
  LIMIT 1
)
AND state IN ('pending', 'failed');
```

Run this inside a `better-sqlite3` transaction. After running it, check the
`.changes` count from the statement result:
- `changes === 1` → this worker won the claim; fetch the job by id and
  execute it.
- `changes === 0` → nothing was claimable right now; sleep `poll-interval-ms`
  and try again.

This is what guarantees "no duplicate processing" — it's a single atomic
statement, not a read-then-write (which would race).

## 6. Job lifecycle, retries, and exponential backoff

States: `pending → processing → completed`, or `processing → failed
(retryable) → pending-again-after-backoff`, or `→ dead` (permanent, this is
the DLQ).

**Attempt-counting semantics (define this precisely — this is exactly the
kind of subtlety the "Assumptions & Trade-offs" section of the README should
call out):**

- `attempts` = number of executions that have been *consumed* so far.
- When a job is claimed, do **not** increment `attempts` yet — the claim
  represents "attempt number `attempts + 1` is starting."
- When execution finishes (success, failure, or timeout):
  - **Exit code 0 → `completed`.** Done.
  - **Non-zero exit code, command not found, or timeout → increment
    `attempts` by 1**, then:
    - if `attempts >= max_retries` → `state = 'dead'` (moved to DLQ)
    - else → `state = 'failed'`, and set
      `next_attempt_at = now + (backoff_base ^ attempts) seconds`
- Interpret `max_retries` as **"maximum total attempts allowed,"** not
  "retries after the first try." (E.g. `max_retries: 3` means the job gets
  exactly 3 executions total, then goes to DLQ.) This is genuinely ambiguous
  in the spec — **explicitly document this interpretation as an assumption
  in the README.**

Backoff formula must literally be `delay = base ^ attempts` seconds, using
the `backoff-base` config value (default `2`), as the assignment specifies.

## 7. Job execution requirements

- Execute `command` via a shell (`sh -c "<command>"` / `cmd /c` on Windows)
  so shell builtins and pipes work.
- Capture **stdout and stderr** in full and store them on the job row
  (bonus: "Job output logging" — implement this, it's low effort and high
  value).
- Enforce a **per-job timeout** (`timeout_seconds`, falling back to
  `default-timeout-s` from config). If the command doesn't exit in time, kill
  the process tree and treat it as a failure with `last_error = "timeout after Ns"`
  (bonus: "Job timeout handling" — implement this).
- A command that doesn't exist (`ENOENT` / exit code 127) must be treated as
  a normal failure, not crash the worker process.

## 8. Crash recovery / stale-lock reaper (this is your key differentiator)

If a worker process is killed (`kill -9`, power loss, OOM) while a job is
`processing`, that job would otherwise be stuck forever with no worker
coming back to it. Implement a **reaper**: on a timer (every few seconds),
any worker process scans for jobs where:

```sql
state = 'processing' AND locked_at < (now - stale_timeout_s)
```

For each one found, treat it exactly like a failed execution attempt
(increment `attempts`, apply the same dead-vs-retry branching from Section
6, and clear `worker_id`/`locked_at`). Also remove/mark stale rows in the
`workers` table whose `last_heartbeat` is too old, so `queuectl status`
never reports a dead worker as active.

This isn't in the PDF's explicit requirements, but it directly answers the
grading rubric's "Robustness — handles edge cases and concurrency safely"
line, and it's the single most common thing that separates a toy
implementation from a real one. **Implement it.**

## 9. Graceful shutdown

`queuectl worker stop`:
- Sends a stop signal to running worker processes (write a "stopping" flag
  the worker checks between jobs, or send `SIGTERM`).
- A worker that receives this **finishes the job it's currently executing**,
  updates the DB, marks itself `stopped` in the `workers` table, and only
  then exits.
- It must **not** pick up a new job once told to stop.
- Support `--timeout <seconds>` after which a still-running worker is force
  killed (`SIGKILL`) — document this trade-off in the README.
- On unclean process death (no stop command, just killed), the reaper from
  Section 8 is what protects the job — this is why both mechanisms exist
  together.

**🔄 Job Lifecycle**
| State | Description |
|---|---|
| pending | Waiting to be picked up by a worker |
| processing | Currently being executed |
| completed | Successfully executed |
| failed | Failed, but retryable |
| dead | Permanently failed (moved to DLQ) |

**💻 CLI Commands**
| Category | Command Example | Description |
|---|---|---|
| Enqueue | `queuectl enqueue '{"id":"job1","command":"sleep 2"}'` | Add a new job to the queue |
| Workers | `queuectl worker start --count 3` | Start one or more workers |
| Workers | `queuectl worker stop` | Stop running workers gracefully |
| Status | `queuectl status` | Show summary of all job states & active workers |
| List Jobs | `queuectl list --state pending` | List jobs by state |
| DLQ | `queuectl dlq list` / `queuectl dlq retry job1` | View or retry DLQ jobs |
| Config | `queuectl config set max-retries 3` | Manage configuration (retry, backoff, etc.) |

**⚙️ System Requirements**

1. **Job Execution**
   - Each worker must execute the specified command (e.g. `sleep 2`, `echo hello`, etc.)
   - Exit codes should determine success or failure.
   - Commands that fail or are not found should trigger retries.

2. **Retry & Backoff**
   - Failed jobs retry automatically.
   - Implement exponential backoff: `delay = base ^ attempts` seconds
   - Move to DLQ after `max_retries`.

3. **Persistence**
   - Job data must persist across restarts.
   - Use file storage (JSON) or SQLite/embedded DB or anything you think is best for this usecase.

4. **Worker Management**
   - Multiple workers can process jobs in parallel.
   - Prevent duplicate processing (locking required).
   - Implement graceful shutdown (finish current job before exit).

5. **Configuration**
   - Allow configurable retry count and backoff base via CLI.

**🧪 Expected Test Scenarios**
1. Basic job completes successfully.
2. Failed job retries with backoff and moves to DLQ.
3. Multiple workers process jobs without overlap.
4. Invalid commands fail gracefully.
5. Job data survives restart.
